# Deploying Aptimizer to Render — frontend and backend as two services

This is the walk-through for the two-service setup described in `render.yaml`:

```
browser ──► aptimizer-web  (nginx + the React build)   https://aptimizer-web.onrender.com
                │
                │  /api/* proxied by nginx
                ▼
            aptimizer-api  (FastAPI)                   https://aptimizer-api.onrender.com
                │
                ▼
            MongoDB Atlas  (your cluster)
```

Both containers bind to whatever port Render assigns, so nothing needs a port number typed
in anywhere.

**Why this shape.** The browser only ever calls `aptimizer-web`. The web container forwards
`/api/*` to the API itself. Nothing is cross-origin, so there is no CORS preflight that can
fail — which is the whole point, see below.

---

## 0. Why the earlier attempt said "Network Error"

That message comes from axios, and it means **the browser never received an HTTP response
at all**. It is not a credentials problem: wrong credentials would have answered
`Invalid email or password`, and a wrong URL would have answered `404`. There are only
three realistic causes, and all three are configuration, not code:

| Cause | What the browser sees | Why it happened |
|---|---|---|
| **CORS** — `FRONTEND_URL` on the API did not match the frontend's origin exactly (scheme, host, port, or a trailing slash) | preflight rejected, request never sent | classic two-service mistake; the old `DEPLOY.md` Route B asked for a build-time backend URL *and* a CORS origin, and both had to agree |
| **Wrong or unreachable API** — the bundle was built with an API base like `http://...` while the page is `https://` (mixed content), or with a stale/incorrect host | connection blocked or refused | the API URL is baked into the JS bundle at build time, so a typo needs a *rebuild*, not an env change |
| **API asleep or crashed** — free instances sleep after 15 minutes, and a bad `MONGO_URL` makes the API exit on boot | first request times out | `MONGO_URL` must be a reachable Atlas string |

What changed:

- The web container proxies `/api/*`, so **CORS cannot be involved** and the API URL is no
  longer baked into the bundle at build time — `API_UPSTREAM` is read when the container
  starts.
- `backend/Dockerfile` now binds to Render's `$PORT` instead of a hardcoded 8000.
- nginx waits up to 300 s for the API, which covers a cold start of a sleeping free instance.

If you would rather have **no** moving parts at all, skip to
[Option B: one service](#option-b--one-service-no-cors-to-configure).

## 1. Before you touch Render

**MongoDB Atlas** (free M0 is enough — the app stores JSON documents, not files):

1. Create an account at mongodb.com/cloud/atlas, create a free **M0** cluster.
2. *Database Access* → add a user with a password (avoid `@`, `/`, `:` in the password, or
   URL-encode them).
3. *Network Access* → allow `0.0.0.0/0`. Render's outbound addresses are not fixed on the
   free plan, and the database still requires the username and password.
4. *Connect → Drivers* → copy the string and substitute your password:

   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority
   ```

**A Gemini API key** at aistudio.google.com. Without at least one AI key, APT and the AI
reports disable themselves (with a reason) but the rest of the app works.

**The code on GitHub**, including the updated `render.yaml`, `backend/Dockerfile`,
`frontend/Dockerfile` and `frontend/nginx.conf` from this workspace. Commit and push those
yourself — nothing here pushes for you:

```bash
git add render.yaml backend/Dockerfile frontend/Dockerfile frontend/nginx.conf RENDER_DEPLOY.md
git commit -m "Deploy frontend and backend to Render as two services"
git push
```

## 2. Create both services from the Blueprint

1. render.com → sign in with GitHub → **New → Blueprint**.
2. Pick the repository. Render reads `render.yaml` and proposes **two** services:
   `aptimizer-api` and `aptimizer-web`. Leave the branch as `main`.
3. It prompts for each value marked `sync: false`:

   | Service | Variable | What to enter |
   |---|---|---|
   | `aptimizer-api` | `MONGO_URL` | the Atlas string from step 1 |
   | `aptimizer-api` | `ADMIN_PASSWORD` | a password you choose — this seeds the first admin on boot |
   | `aptimizer-api` | `GEMINI_API_KEY` | your key (leave blank if you have none) |

   `JWT_SECRET` is generated by Render — do not set it by hand. `ADMIN_EMAIL` is preset to
   `admin@aptimizer.com`; change it in the dashboard if you want your own address.
   Everything else, including `API_UPSTREAM`, is already filled in.
4. **Apply**. Two builds run at once; the first takes 8–15 minutes (npm install plus pip
   install of numpy/pandas/shapely/ifcopenshell).

**If the API's URL is not `https://aptimizer-api.onrender.com`** — Render appends a suffix
when the name is taken — then open `aptimizer-web` → *Environment* → set `API_UPSTREAM` to
the real API URL → *Save, rebuild and deploy*. The container reads it at start, so no
rebuild of the React bundle is involved.

## 3. Check the wiring before you blame the frontend

Run both of these. The second one proves the proxy is right:

```bash
curl -i https://aptimizer-api.onrender.com/api/
# {"service":"Aptimizer API","status":"ok"}

curl -i https://aptimizer-web.onrender.com/api/
# the same JSON, arriving through nginx
```

- First fails → the API service itself: read its logs in the dashboard. `KeyError: 'MONGO_URL'`
  means the variable is missing; a timeout means it is still cold-starting (~1 minute) or
  Atlas is refusing the connection.
- First works, second fails → `API_UPSTREAM` on `aptimizer-web` is wrong. nginx refuses to
  start when the upstream hostname does not resolve, so the logs say
  `host not found in upstream` — that is this exact mistake.

Then open **https://aptimizer-web.onrender.com**, sign in with the admin email and
`ADMIN_PASSWORD`, and confirm a project loads.

## 4. If login still says "Network Error"

Open the browser's developer tools → *Network*, submit the form, and look at the request to
`/api/auth/login`:

| What you see | Cause | Fix |
|---|---|---|
| **502** on `/api/auth/login` | the API is unreachable from nginx | the API service is asleep, crashed, or `API_UPSTREAM` is wrong — check step 3 |
| **CORS error** in the console, request never sent | the bundle was built earlier with an absolute `REACT_APP_BACKEND_URL`, so the browser is calling the API directly | delete `REACT_APP_BACKEND_URL` from `aptimizer-web`'s environment, then **Manual Deploy → Clear build cache & deploy** |
| **"host not found in upstream"** in the web service's logs | `API_UPSTREAM` typo | correct it and redeploy |
| **504 / takes ~1 min then succeeds** | the free API was asleep | expected on free; open `/api/` first to warm it, or move to a paid plan |
| **404 with HTML** | a request went to the static site instead of the proxy | confirm the frontend service is a **Docker** web service, not a static site |

> A static site has no nginx and therefore no `/api` proxy. If you deploy the frontend as a
> static site you must instead set `REACT_APP_BACKEND_URL=https://<api>.onrender.com` in its
> environment **before** the build and `FRONTEND_URL=https://<web>.onrender.com` on the API.
> The proxy route above needs neither.

## 5. Free plan arithmetic

- Each free web service gets 0.1 CPU / 512 MB and sleeps after 15 minutes idle. That is why
  `WEB_CONCURRENCY` is pinned to 1 for the API: the library imports alone fill 512 MB, and
  two worker processes do not fit.
- The free allowance is **750 instance hours per month** across your workspace, counted
  while instances are awake. Two services that are only awake when used stay inside it; two
  services pinned awake do not.
- Sleeping is the main symptom people mistake for a bug. `curl` the API's `/api/` before
  demonstrating the app, and the cold start happens while you talk.

## Option B — one service, no CORS to configure

The repository's root `Dockerfile` (used by the render.yaml that used to live here) builds
the React app, the API and nginx into **one** container, publishing everything on one URL.
The API is then same-origin by construction. It is the smallest possible deployment and the
hardest to get wrong; the two-service split above exists so the API and web app can be
scaled and restarted independently.

To use it, replace `services:` in `render.yaml` with:

```yaml
services:
  - type: web
    name: aptimizer
    runtime: docker
    dockerfilePath: ./Dockerfile
    region: singapore
    plan: free
    healthCheckPath: /api/
    envVars:
      - key: MONGO_URL
        sync: false
      - key: DB_NAME
        value: aptimizer
      - key: JWT_SECRET
        generateValue: true
      - key: ADMIN_EMAIL
        value: admin@aptimizer.com
      - key: ADMIN_PASSWORD
        sync: false
      - key: GEMINI_API_KEY
        sync: false
```

and delete the two-service block. `docker-compose.yml` remains the local equivalent.

## 6. Updating a live deployment

Push to the connected branch and Render redeploys automatically. Each service has a
`buildFilter` in `render.yaml`, so a push that only touches `frontend/` rebuilds the web
service and leaves the API alone (and the reverse). Each service also has its own Docker
build context, so the API image never carries the React source and vice versa.

If you ever add code at the repository root that either app needs, delete the two
`buildFilter` blocks — while they exist, root-level changes do not trigger anything.

Rolling back: *Deploys* → pick an earlier deploy → **Redeploy**. Data lives in Atlas, so it
survives.
